# LMS MVP — дизайн

Дата: 2026-11-08
Статус: на затвердженні командою

## 1. Контекст і мета

Лабораторна робота № 2 «Командна розробка програмного продукту згідно стратегії
екстремального програмування». Оцінюється насамперед **процес XP** і **тести**, а не
обсяг функціоналу. Продукт — MVP системи керування навчанням (LMS).

Вимоги завдання, які має покрити проєкт:

- розподіл ролей у команді за XP;
- реалізація за практиками XP (user stories, planning game, короткі ітерації, парне
  програмування, TDD, колективне володіння кодом, малі релізи);
- тестування: щонайменше 1 модульний, 1 інтеграційний, 1 e2e тест;
- облік задач на дошці (команда використовує **ClickUp**; слід підтвердити у викладача,
  що він приймається замість Trello/Jira);
- звіт: код, звіт про тестування, протокол роботи програми, знімки дошки, висновки.

Критерій успіху: усі 8 функцій нижче працюють на демо, система піднімається однією
командою через Aspire, є тести всіх трьох видів, і є матеріал для звіту з 3–4 ітерацій.

## 2. Команда

3 особи: одна пише на .NET і React, дві — на Python. Звідси розподіл зон: C#-частина
(AppHost, gateway) і фронтенд — на .NET/React-розробнику, бізнес-логіка — у двох
Python-сервісах.

## 3. Обсяг

### Входить у MVP

Ролі в системі: `teacher` (викладач) і `student` (студент).

1. Реєстрація та вхід із роллю (через Keycloak).
2. Викладач створює курс; студент бачить каталог і записується на курс.
3. Викладач додає до курсу завдання з описом, дедлайном і максимальним балом.
4. Студент здає завдання (текст та/або файл).
5. Викладач бачить здачі, ставить оцінку з коментарем; студент бачить свою оцінку.
6. Матеріали курсу: модулі, текстові матеріали (markdown) і прикріплені файли.
7. Квізи: викладач створює питання, студент проходить, оцінка ставиться автоматично.
8. Журнал оцінок: таблиця «студенти × завдання/квізи» для викладача, власні оцінки для
   студента.

### Не входить (кандидати, якщо залишиться час)

Аналітика по курсу, нагадування про дедлайни, експорт журналу в Excel, чати, відео,
календар, email-сповіщення, адмін-панель, мобільна версія, CI.

## 4. Архітектура

```
                    ┌──────────── Keycloak (realm "lms") ────────────┐
                    │ ролі: teacher, student · клієнт lms-web (PKCE) │
                    └───────▲───────────────────────────▲────────────┘
                   логін (OIDC)                      JWKS (публічні ключі)
                            │                           │
 React SPA ──JWT──► C# Gateway (YARP) ──JWT──► courses-service    (Python, FastAPI) ─► Postgres: courses_db
                     перевірка токена   └────► assessment-service (Python, FastAPI) ─► Postgres: assessment_db
                     і ролі на маршрутах
 └────────────────── усе піднімає Aspire AppHost (C#) ──────────────────┘
```

### Компоненти

| Компонент | Відповідальність |
|---|---|
| `Lms.AppHost` | Aspire: піднімає Keycloak, Postgres (2 БД), обидва Python-сервіси, gateway, web; передає адреси й рядки підключення через `WithReference` |
| `Lms.ServiceDefaults` | OpenTelemetry, health checks для .NET-частини |
| Keycloak | Користувачі, логін, самореєстрація (роль за замовчуванням `student`), видача JWT. Realm імпортується з `infra/keycloak/realm-lms.json` разом із тестовими юзерами |
| `Lms.Gateway` | Єдина точка входу: маршрутизація `/api/courses/*` → courses-service, `/api/assessment/*` → assessment-service; валідація JWT; грубі політики ролей на маршрутах; CORS |
| `courses-service` | Курси, запис на курс, модулі, матеріали, файли матеріалів |
| `assessment-service` | Завдання, здачі, оцінювання, квізи з автоперевіркою, журнал оцінок |
| `web` | React + Vite + TypeScript, логін через `react-oidc-context` |

### Ключові рішення

- **Користувачі живуть лише в Keycloak.** Сервіси зберігають `user_id` = claim `sub`.
  Ім'я береться з токена в момент дії й зберігається як знімок (`student_name`,
  `teacher_name`). Синхронізації користувачів немає.
- **Двошарова авторизація.** Gateway перевіряє валідність токена й роль на маршруті.
  Python-сервіси самі валідують той самий JWT за JWKS Keycloak (PyJWT) і перевіряють
  доступ до конкретного ресурсу (власник курсу, записаний студент).
- **Одна міжсервісна залежність:** `assessment-service` → `courses-service` через
  внутрішні ендпоінти `/internal/*`, які gateway не відкриває назовні.
- **Окрема БД на сервіс** на одному сервері Postgres. Спільних таблиць немає.
- **Файли** зберігаються на диску в томі, який Aspire монтує кожному сервісу. Ліміт
  10 МБ на файл.
- **Python-інструменти:** `uv` для залежностей і запуску, FastAPI, SQLAlchemy 2,
  Alembic, Pydantic, ruff. AppHost запускає Python-сервіси через інтеграцію Aspire для
  Python (uvicorn + uv).

## 5. Модель даних

Усі `id` — UUID. Усі `*_id` користувачів — `sub` з Keycloak (рядок).

### courses-service → `courses_db`

| Таблиця | Поля |
|---|---|
| `courses` | `id`, `title`, `description`, `teacher_id`, `teacher_name`, `created_at` |
| `enrollments` | `course_id`, `student_id`, `student_name`, `enrolled_at`; PK (`course_id`, `student_id`) |
| `modules` | `id`, `course_id`, `title`, `position` |
| `materials` | `id`, `module_id`, `title`, `kind` (`text` \| `file`), `content_md`, `file_key`, `file_name`, `position` |

### assessment-service → `assessment_db`

| Таблиця | Поля |
|---|---|
| `assignments` | `id`, `course_id`, `title`, `description`, `due_at`, `max_points` |
| `submissions` | `id`, `assignment_id`, `student_id`, `student_name`, `text_answer`, `file_key`, `file_name`, `submitted_at`, `is_late`, `grade`, `feedback`, `graded_at`; unique (`assignment_id`, `student_id`) |
| `quizzes` | `id`, `course_id`, `title` |
| `questions` | `id`, `quiz_id`, `position`, `type` (`single` \| `multiple` \| `short_text`), `text`, `points`, `options` (jsonb: `[{id, text}]`), `correct` (jsonb: id варіантів або список допустимих рядків) |
| `quiz_attempts` | `id`, `quiz_id`, `student_id`, `student_name`, `answers` (jsonb), `score`, `max_score`, `details` (jsonb), `submitted_at`; unique (`quiz_id`, `student_id`) |

## 6. API

Зовнішні шляхи вказано так, як їх бачить фронтенд через gateway.

### courses-service (`/api/courses`)

| Метод і шлях | Хто | Опис |
|---|---|---|
| `GET /` | усі | Каталог курсів |
| `POST /` | teacher | Створити курс |
| `GET /mine` | усі | Курси, де я власник або записаний |
| `GET /{id}` | власник, записаний студент | Курс з модулями та матеріалами |
| `POST /{id}/enroll` | student | Записатися на курс |
| `POST /{id}/modules` | власник | Додати модуль |
| `POST /modules/{id}/materials` | власник | Додати матеріал (текст або файл) |
| `GET /materials/{id}/file` | власник, записаний студент | Завантажити файл матеріалу |

Внутрішні (лише для `assessment-service`):

| Метод і шлях | Відповідь |
|---|---|
| `GET /internal/courses/{id}/access?user_id=…` | `{"access": "owner" \| "student" \| "none"}` |
| `GET /internal/courses/{id}/students` | `[{student_id, student_name}]` |

### assessment-service (`/api/assessment`)

| Метод і шлях | Хто | Опис |
|---|---|---|
| `POST /courses/{id}/assignments` | власник | Створити завдання |
| `GET /courses/{id}/assignments` | власник, студент | Список завдань (студенту — зі статусом своєї здачі) |
| `PUT /assignments/{id}/submission` | student | Здати або перездати |
| `GET /assignments/{id}/submissions` | власник | Усі здачі |
| `GET /submissions/{id}/file` | власник, автор здачі | Файл здачі |
| `POST /submissions/{id}/grade` | власник | Оцінка + коментар |
| `POST /courses/{id}/quizzes` | власник | Створити квіз з питаннями |
| `GET /courses/{id}/quizzes` | власник, студент | Список квізів |
| `GET /quizzes/{id}` | власник, студент | Квіз; студенту без поля `correct` |
| `POST /quizzes/{id}/attempt` | student | Здати квіз; відповідь: `score`, `max_score`, `details` |
| `GET /courses/{id}/gradebook` | власник | Журнал: студенти × (завдання + квізи) + сума |
| `GET /courses/{id}/my-grades` | student | Власні оцінки по курсу |

## 7. Бізнес-правила

1. **Запис на курс відкритий:** без ключів і підтверджень.
2. **Здача завдання** може оновлюватися, доки її не оцінено; після оцінки — 409.
   Здача після `due_at` приймається з `is_late = true`.
3. **Квіз проходиться один раз**; повторна спроба — 409.
4. **Перевірка квізів** — чистий модуль `grading.py` без БД і HTTP:
   - `single`: повний бал, якщо обрано правильний варіант, інакше 0;
   - `multiple`: повний бал лише за точний збіг множини обраних варіантів з правильною,
     без часткових балів;
   - `short_text`: повний бал, якщо нормалізована відповідь збігається з одним із
     допустимих варіантів. Нормалізація: обрізати пробіли по краях, звести до нижнього
     регістру, кілька пробілів поспіль замінити одним;
   - питання без відповіді — 0 балів;
   - `details` містить для кожного питання: `question_id`, `earned`, `points`, `correct`
     (bool).
5. **Оцінки в балах, без ваг:** підсумок курсу дорівнює сумі балів за завдання й квізи.
   Неоцінене або нездане — `null`, у суму не входить.
6. **Ролі:** нові користувачі через самореєстрацію отримують `student`. Роль `teacher`
   призначається в Keycloak вручну; у realm-файлі є заздалегідь створені викладачі.

## 8. Потоки даних

### Вхід

1. SPA перенаправляє на Keycloak (Authorization Code + PKCE, клієнт `lms-web`).
2. Keycloak повертає access token (JWT з `sub`, `name`, `realm_access.roles`).
3. Токен зберігається в пам'яті SPA і додається до кожного запиту `/api/*`.
   Оновлення токена — тихе, у фоні.

### Проходження квізу

```
React ─POST /api/assessment/quizzes/{id}/attempt──► Gateway
  Gateway: JWT валідний? роль student? ── ні → 401/403
  └─► assessment-service: валідує JWT, бере quiz.course_id
        └─► courses-service GET /internal/courses/{cid}/access?user_id=sub
              не "student" → 403
        спроба вже є → 409
        grading.grade(questions, answers) → score, details
        зберегти quiz_attempt → 201 {score, max_score, details}
```

### Журнал оцінок

`assessment-service` перевіряє `access == owner`, отримує студентів із
`/internal/courses/{id}/students`, бере здачі й спроби зі своєї БД і збирає таблицю.

## 9. Обробка помилок

| Ситуація | Код | Що бачить користувач |
|---|---|---|
| Токен відсутній або протух | 401 | Тихе оновлення; якщо не вдалося — перехід на логін |
| Немає ролі або доступу до ресурсу | 403 | «Немає доступу» |
| Ресурс не існує | 404 | Сторінка «Не знайдено» |
| Невалідні дані | 422 | Підсвічені поля форми |
| Повторна спроба квізу / зміна оціненої здачі | 409 | Пояснювальне повідомлення |
| Файл більше 10 МБ | 413 | «Файл завеликий» |
| `courses-service` недоступний для `assessment-service` (таймаут 3 с, без ретраїв) | 503 | Toast «Сервіс тимчасово недоступний» |
| Python-сервіс недоступний для gateway | 502 | Той самий toast |

Формат тіла помилки в обох Python-сервісах — `{"detail": "текст"}`. Gateway передає
його без змін.

## 10. Спостережуваність

- .NET-проєкти підключають `Lms.ServiceDefaults`.
- Python-сервіси підключають `opentelemetry-instrumentation-fastapi` з OTLP-експортом
  у дашборд Aspire (адресу Aspire передає через `OTEL_EXPORTER_OTLP_ENDPOINT`).
- У дашборді видно логи всіх сервісів і трейс «gateway → assessment → courses».
  Скріни дашборду йдуть у розділ звіту «протокол роботи програми».

## 11. Тестування

| Вид | Що перевіряє | Інструмент |
|---|---|---|
| Модульний | `grading.py`: усі 3 типи питань, порожні відповіді, нормалізація тексту | pytest |
| Модульний | Правила доступу до курсу (власник / студент / сторонній) | pytest |
| Модульний | Перетворення `realm_access.roles` у claims ролей ASP.NET | xUnit |
| Інтеграційний | Ендпоінти кожного сервісу з реальним Postgres | pytest + testcontainers |
| Інтеграційний | Наскрізний ланцюжок: Aspire піднімає систему, тест отримує токен тестового юзера, викладач створює курс і квіз, студент записується, проходить квіз і отримує бал | xUnit + `Aspire.Hosting.Testing` |
| E2E | У браузері: студент логіниться і здає завдання; викладач ставить оцінку; студент бачить оцінку | pytest-playwright |

- Для тестів без браузера realm містить клієнт `lms-tests` з дозволеним логіном за
  паролем (Direct Access Grants). Він існує лише в dev-realm.
- **TDD:** для `grading.py` і правил доступу тест пишеться першим, окремими комітами
  `test: …` (червоний) і `feat: …` (зелений). Історія комітів — доказ test-first у звіті.
- **CI поки не робимо.** Замість нього — скрипт `scripts/test-all.ps1`, який запускає
  всі тести локально. Правило команди: перед злиттям у `main` скрипт має проходити;
  інтегруємося в `main` щодня маленькими змінами. (У звіті це варто описати як практику
  безперервної інтеграції без CI-сервера і згадати як недолік.)

## 13. Процес XP

### Ітерації

Тривалість — 1 тиждень. Кожна закінчується релізом (тег `v0.x`) і демо.

| Ітерація | Функції | Результат |
|---|---|---|
| 1. Скелет | 1, 2 | Усе піднімається через Aspire; логін, каталог, запис на курс; **по одному тесту кожного виду вже є** |
| 2. Завдання | 3, 4, 5 | Цикл «завдання → здача → оцінка» + e2e на нього |
| 3. Контент і квізи | 6, 7 | Матеріали курсу, квізи з автоперевіркою |
| 4. Журнал | 8 + полірування | Журнал оцінок, скріни, звіт |

Якщо часу 3 тижні — ітерації 3 і 4 зливаються; функція 8 першою йде під виліт.

### Парне програмування

Пари змінюються щоітерації, щоб кожен попрацював з кожним і в різних частинах коду
(C#, Python, React). Це забезпечує колективне володіння кодом.

### ClickUp

- Список `Backlog` — user stories з полями *Story points* (1/2/3/5) і *Pair*.
- Кожна ітерація — Sprint.
- Статуси: `To Do → In Progress → Review → Done`.
- Кожна story має підзадачі, включно з тестовими.
- Наприкінці ітерації — скрін Board view і burndown для звіту.

## 14. Відкриті питання

- Чи приймає викладач ClickUp замість Trello/Jira.
